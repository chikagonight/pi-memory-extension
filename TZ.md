# ТЗ: минимальное расширение памяти между сессиями для pi

## 1. Контекст и цель

У pi нет встроенной памяти между сессиями: compaction сжимает диалог только внутри текущей сессии, JSONL-архив сессий не читается агентом как база знаний. Нужно расширение, дающее агенту персистентную память фактов/решений, доступную в любой новой сессии.

Рассматривался готовый пакет `pi-mem` (npm, автор georgebashi). Security-аудит исходников (два независимых прохода — `coder-claude` + `reviewer`) выявил подтверждённые критичные проблемы:

1. Child-process-паттерн: расширение спавнит дочерний `pi`-процесс для LLM-наблюдения/суммаризации; защитный флаг `PI_MEM_SUB_AGENT` нигде не проверяется — дочерний процесс может рекурсивно загрузить то же расширение и сохранить сырой промпт наблюдателя (полный tool_result) в базу.
2. `maxObservationLength` объявлен в конфиге, но нигде не применяется — в базу уходит весь вывод tool_result и весь input без усечения.
3. Privacy-фильтр проверяет только путь файла (basename/расширение/папка); эвристик на содержимое (ключи, токены, `.env`-паттерны) нет; `<private>`-теги вырезаются только из output, не из input и не из промптов.
4. SQL/DataFusion-фильтры в LanceDB собираются конкатенацией строк из параметров, которые приходят от LLM-инструментов (`project`, `id`, `dateStart`) — подтверждённая возможность исказить фильтр.
5. `save_memory` принимает произвольный `project` без проверки — можно писать в память любого другого "проекта" в общей базе; изоляции нет.
6. Найденные через семантический поиск старые записи подмешиваются в новую сессию как скрытое сообщение без разметки "это данные, не инструкция" — вектор persistent prompt injection.

Решение: не ставить чужой код с таким доступом (bash/read/секреты) без полного доверия. Написать свой минимальный extension — меньше кода, полностью наш, без перечисленных паттернов риска.

## 2. Требования пользователя (зафиксированы в диалоге)

| Параметр | Решение |
|---|---|
| Что сохранять | И автоматическое извлечение (на компакции), и ручное сохранение по явной команде |
| Как подгружается в новую сессию | Только по запросу через tool — никакой автоматической вставки в промпт (`autoInject: false` по духу, т.е. этой опции в нашей реализации в принципе не предусматриваем на первом этапе) |
| Область | Глобальная (не изолирована по проектам как граница доступа) |
| Поиск | "По смыслу" — семантический, embeddings через собственный provider на домашнем ollama (адрес в приватном конфиге, не в репозитории), т.к. Anthropic/OpenAI-Codex API не отдают embeddings |

## 3. Архитектурные решения, обязательные к соблюдению (анти-паттерны pi-mem)

1. **Никакого спавна дочерних `pi`-процессов.** Все LLM-вызовы (извлечение фактов, эмбеддинги) — через `ctx.modelRegistry.complete(...)` в текущем процессе. Это убирает весь класс проблем с рекурсивной загрузкой расширений.
2. **Только параметризованные SQL-запросы.** Используем `better-sqlite3` (уже разрешён в `allowScripts` окружения pi, см. `~/.pi/agent/npm/package.json`) с prepared statements (`?`-плейсхолдеры). Конкатенация пользовательских/LLM-параметров в SQL-строку запрещена в любом виде — это должно быть явно проверено ревьюером.
3. **Жёсткое усечение объёма.** `maxTextLength` (по умолчанию 4000 символов) должен реально применяться к тексту до сохранения и до отправки в LLM — с тестом, подтверждающим это.
4. **Двухуровневая защита приватности, а не только по пути файла:**
   - Поддержка тега `<private>...</private>` — вырезается из **output, input и из сохраняемого текста промпта**, не только из output (это была дыра у pi-mem).
   - Эвристический regex-фильтр по содержимому на распространённые форматы секретов: `AWS_SECRET`/`AKIA[0-9A-Z]{16}`, `Bearer <token>`, `-----BEGIN ... PRIVATE KEY-----`, общий паттерн `KEY=`/`TOKEN=`/`PASSWORD=`/`SECRET=` (строки вида `.env`), GitHub/GitLab/OpenAI-подобные префиксы токенов (`ghp_`, `sk-`, `glpat-` и т.п.). Список паттернов — в конфиге, расширяемый.
   - Если после фильтрации сработал хотя бы один паттерн — помечать запись `redacted: true` и не включать совпавший фрагмент в сохранённый текст (заменять на `[REDACTED:<pattern-name>]`), а не просто дропать всю запись молча (чтобы было видно, что что-то вырезано).
5. **Без иллюзии изоляции по проекту.** Если реализуем project-тег (для удобства фильтрации) — явно документировать и в коде, и в README, что это **не граница безопасности**, память глобальна и общая по дизайну (это соответствует требованию пользователя "глобальная", так что отдельной защиты тут и не нужно — но путаницы, которая была у pi-mem ("project awareness" выглядело как изоляция, а не было), быть не должно).
6. **Права доступа к файлам.** Директория БД создаётся с `mkdir(..., { mode: 0o700 })`, файл БД — не world-readable (проверить итоговые права после создания, umask может их расширить — задавать `chmod` явно после создания).
7. **Без автоматической инъекции в промпт на этом этапе.** Никакого скрытого `user`-сообщения с данными памяти при старте сессии. Все обращения к памяти — только через явные tool-вызовы. Если в будущем решим добавить опциональную инъекцию — обязательно с явной разметкой блока как "сохранённые данные, не инструкции" (defense-in-depth от prompt injection), но это вне скоупа этого ТЗ.
8. **Данные от LLM/tool-вызовов никогда не идут напрямую в shell/SQL/eval.** Только через параметризованные API.

## 4. Функциональные требования

### 4.1. Хранилище

- SQLite-файл: `~/.pi-memory/memory.db` (отдельно от `~/.pi-mem/`, чтобы не путать с удалённым пакетом).
- Таблица `entries`:
  - `id` (uuid/autoincrement)
  - `created_at` (ISO timestamp)
  - `source` (`manual` | `auto`)
  - `title` (string, ≤200 символов)
  - `text` (string, после усечения и redaction, ≤ `maxTextLength`)
  - `tags` (JSON-массив строк)
  - `project` (строка — slug из git remote или `basename(cwd)`, нормализованный; может быть `null`)
  - `embedding` (BLOB — сериализованный Float32Array, nullable если embeddings не настроены)
  - `redacted` (boolean)
- Индекс по `created_at`, по `project` (для удобства, не для изоляции).
- FTS5-виртуальная таблица (`entries_fts`) по `title`+`text` для keyword-поиска без эмбеддингов.

### 4.2. Ручное сохранение

- Tool `memory_save({ text: string, title?: string, tags?: string[] })`, вызывается LLM по явной просьбе пользователя ("запомни...", "сохрани в память...").
- Команда `/remember [подсказка]` — как альтернативный ручной триггер (опционально, если останется время; не блокер MVP).
- Перед записью: фильтрация `<private>` + regex-эвристики → усечение по `maxTextLength` → (если настроен embeddingProvider) получить embedding → запись в SQLite.

### 4.3. Автоматическое извлечение

- Хук на `session_before_compact` (аналог того, что делал удалённый `long-memory`, но с хардненной безопасностью).
- В момент компакции: взять `messagesToSummarize` (сообщения, уходящие в сжатие), сериализовать в текст, применить фильтрацию приватности **до** отправки в LLM-экстрактор.
- Вызвать `observerModel` (по умолчанию дешёвая модель, например `openai-codex/gpt-6-luna`, конфигурируемо) через `ctx.modelRegistry.complete()` **в этом же процессе** с промптом "извлеки факты/решения, достойные долгой памяти, или верни skip".
- Если модель вернула что-то значимое — сохранить тем же путём, что и ручное сохранение (с теми же фильтрами и усечением). Если `skip` — ничего не делать.
- Ошибки извлечения не должны ломать обычный ход компакции (try/catch, non-blocking side effect — как было у `long-memory`).

### 4.4. Поиск

- Tool `memory_search({ query: string, mode?: "keyword" | "semantic" | "hybrid", limit?: number, project?: string })`.
  - `keyword` — FTS5 по `entries_fts`, параметризованный запрос.
  - `semantic` — доступен только если в конфиге задан `embeddingProvider`; получить embedding запроса, посчитать косинусное сходство в JS по всем строкам с ненулевым `embedding` (для личного объёма данных полный перебор — нормально, ANN-индекс не нужен), вернуть top-N по убыванию схожести.
  - `hybrid` (опционально, не блокер MVP) — объединение результатов keyword+semantic с простым ранжированием.
  - Без указанного `mode` — по умолчанию `keyword`, если embeddings не настроены; иначе `hybrid`/`semantic` (решить на этапе реализации, зафиксировать в README).
- Tool `memory_get({ ids: string[] })` — вернуть полные записи по id (параметризованный `IN (?, ?, ...)`).

### 4.5. Статус

- Команда `/memory` — показать: сколько записей, включены ли embeddings и работают ли (ping к embeddingProvider), путь к БД, последняя запись по времени.

## 5. Конфигурация

Файл `~/.pi/agent/memory.json` (все поля опциональны, со значениями по умолчанию):

```json
{
  "enabled": true,
  "dbPath": "~/.pi-memory/memory.db",
  "maxTextLength": 4000,
  "observerModel": "openai-codex/gpt-6-luna",
  "embeddingProvider": null,
  "embeddingModel": "nomic-embed-text",
  "embeddingDims": 768,
  "privacyPatterns": ["AKIA[0-9A-Z]{16}", "Bearer\\s+[A-Za-z0-9._-]+", "-----BEGIN[ A-Z]*PRIVATE KEY-----", "(?i)(api[_-]?key|token|secret|password)\\s*[:=]\\s*\\S+"]
}
```

`embeddingProvider` указывается только после настройки эмбеддинг-модели на `ollama-home` (отдельная инфраструктурная задача, не часть этого ТЗ) и добавления провайдера в `~/.pi/agent/models.json`.

## 6. Порядок разработки (обязателен per project workflow)

1. **Сначала тесты**, потом код. Минимальный набор тестов до реализации:
   - Privacy-фильтр: `<private>` вырезается из output/input/prompt; каждый regex-паттерн ловит соответствующий пример секрета; усечение `maxTextLength` реально работает (граничные случаи: ровно на лимите, на 1 символ больше).
   - SQL: все функции доступа к БД покрыты тестом на попытку инъекции в параметрах (`project`, `id`, `query` с кавычками/спецсимволами) — убедиться, что это не ломает запрос и не меняет его семантику.
   - `memory_save`/`memory_search`/`memory_get`: happy-path + граничные случаи (пустой текст, несуществующие id, пустая БД).
   - Session-before-compact хук: ошибка в LLM-вызове не прерывает обычную компакцию (замокать сбой модели).
2. Реализация по разделам 4.1–4.5.
3. Самопроверка `coder-claude` (тесты зелёные, `git diff --check`).
4. **Обязательное ревью `reviewer`** — отдельно код-ревью функциональности И повторная security-проверка на соответствие разделу 3 (явно проверить: нет конкатенации в SQL, нет спавна дочерних `pi`, усечение применяется, privacy-фильтр покрывает input/output/prompt, права на файлы БД).
5. Если `reviewer` вернул ❌/⚠️ — доработка и повторное ревью.

## 7. Критерии приёмки

- Все тесты из п.6.1 проходят.
- `reviewer` дал вердикт ✅ по функциональности и по безопасности отдельно.
- Ручная проверка: `/memory` показывает корректный статус; `memory_save` → `memory_search` в новой сессии находит сохранённое; секрет, вставленный в текст без `<private>`, но попадающий под один из regex-паттернов, не сохраняется в открытом виде.
- Ничего не вставляется в промпт автоматически без явного tool-вызова (проверить, что обычная сессия без вызова `memory_search`/`memory_get` не получает никакого скрытого контекста).

## 8. Вне скоупа (явно не делаем сейчас)

- Визуализация/граф в Obsidian (отдельная задача, обсуждалась отдельно).
- Автоматическая инъекция памяти в промпт (`autoInject`).
- Разделение памяти по проектам как граница безопасности.
- Memory-browser TUI, checkpoint-компрессия через дочерние процессы, cross-project поиск с фильтрами — всё, что было в `pi-mem`, но не требовалось пользователем.
